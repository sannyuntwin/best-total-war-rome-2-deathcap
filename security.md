## 🗃️ Managing Multiple Game Setups

One tool, several games, and the configuration problem nobody plans for.

**The problem**

Settings that suit one title are wrong for another. An aggressive assist tuned
for a fast shooter is absurd in a slow tactical game. Sharing one config means
constant re-tuning.

**The structure that works**

| **Level** | **Holds** |
| --- | --- |
| Base config | keybinds, overlay colours, updater settings |
| Per-game preset | module enablement, tuning values |
| Session overrides | temporary changes you intend to discard |

**Naming that stays usable**

Name presets after the game, not after the settings: `game-a-quiet` beats
`fov12-smooth52`. Six months later the first is still readable.

**Switching cost**

Loading a preset takes under a second and is done before joining a lobby. There
is no reason to run the wrong preset for a session because switching felt like
effort.

**When to fork a preset**

If you change more than two values for one title, fork it. A preset that needs
constant edits is really two presets wearing one name.

**Shared values**

Keybinds and overlay colours belong in the base config precisely so they do not
need repeating in every per-game preset. Duplicating them means changing them
everywhere when one key moves.
